# 실제 사고 연표와 교훈

전부 실제로 발생했다. 각 사고의 **탐지 지연**에 주목한다 — 결제 사고는 터지는 순간이 아니라
누군가 알아차리는 순간에 비용이 확정된다.

## 반복되는 패턴 5가지

**패턴 1 — 조용한 실패가 지배적이다.**
다수 사고가 "예외도 안 나고 로그도 안 남고 그냥 안 되는" 형태였다. 없는 필드와 비교(falsy),
삽입 실패 무시, 스키마 필드 누락으로 조용히 잘림, 알림 미수신. 결제 코드에서는 **모든
분기가 명시적으로 소리를 내야 한다.**

**패턴 2 — 코드가 아니라 설정이 죽는다.**
가장 비싼 #3은 코드 리뷰로 절대 못 잡는다. 엔드포인트 설정, 환경변수 주입, 스토어 콘솔
설정이 실제 사고 원인의 큰 축이다. **감사는 인프라 축을 반드시 포함한다.**

**패턴 3 — 보안 판단이 복구 가능성을 지운다.**
"토큰은 해시만 저장"이 옳아 보였지만, 그 결정이 자동 복구를 불가능하게 만들어 수작업
복구 비용과 장기 피해를 낳았다. **암호화 보관이라는 제3의 선택지를 항상 검토한다.**

**패턴 4 — 탐지 수단이 없으면 지연은 무한하다.**
#3이 2개월 간 것은 "갱신 이벤트 0건"을 아무도 감시하지 않았기 때문이다. 사용자는 항의하지
않고 이탈한다. **결제는 지표로 감시해야 한다.**

**패턴 5 — 초록불 하나는 정상 증거가 아니다.**
HTTP 200, 콘솔 저장 성공, 테스트 알림 수신은 서로 다른 층의 증거다. 테스트 알림이
`unsupported_notification`으로 인박스에 도착하면 전송 경로는 증명되지만 실제 renewal 처리까지
증명된 것은 아니다. **전송·인증·인박스·업무 처리·재검증 가능성을 분리해 판정한다.**

## 이 사고들이 남긴 최소 감시 세트

새 프로젝트에 결제를 붙이면 최소한 이 다섯은 붙인다.

1. **갱신 이벤트 무수신 알림** — 최근 24~48시간 renewal 0건이면 알림
2. **부팅 시 결제 시크릿 검증 알림** — 누락 즉시
3. **미처리 웹훅 누적 알림** — 인박스 적체
4. **합성 테스트 알림 heartbeat** — 운영 인박스 도착 여부
5. **재검증 토큰 보유율** — 레거시 미커버 비율과 백필 진행률

이 감시가 없으면 다음 사고의 탐지 지연도 몇 주 단위가 된다.

## 복구 스크립트 작성 규칙

사고 대응으로 스크립트를 쓸 때 지킨다(#3 복구에서 확립).

- **dry-run이 기본**, `--apply`를 명시해야 실제 반영
- **권한 부여 방향만** 수행. 회수·삭제는 하지 않는다
- 이미 유효한 사용자는 건너뛴다(중복 부여 없음)
- 직접 UPDATE 금지 — 정규 이벤트 적용 함수를 그대로 태워 원장·게이트 계산을 일치시킨다
- 멱등키에 **userId 포함**(한 주문을 여러 계정이 공유하는 경우가 실재)
- 요약 출력: `matched / restored / alreadyValid / notFound / failed`
- 주문번호·토큰은 tracked source에 새로 하드코딩하지 않고 untracked 입력 파일/표준입력으로 받는다
- 실행 전 import/DB 연결을 포함한 dry-run 자체가 독립 실행되는지 확인한다
- 로그와 문서에는 식별자 원문 대신 건수와 결과 요약만 남긴다
