# 결제 무결성 — 필수 항목 14

각 항목은 실제 운영 사고에서 역산했다. "사고 → 왜 못 잡았나 → 필수 구현 → 체크" 순서다.
코드 예시는 TypeScript/Postgres 기준이지만 원리는 스택 무관이다.

---

## 1. 부팅 시 시크릿 검증 + 즉시 알림

**사고:** 스토어 서비스 계정 환경변수 누락으로 안드로이드 결제 검증이 **전수 실패**했다.
실패 응답이 "잘못된 영수증"과 같은 400이라 아무도 몰랐다.

**왜 못 잡았나:** 정상 실패와 장애 실패가 같은 상태코드였다.

**필수 구현**

- 부팅 시 결제 시크릿 존재를 검증하고, 누락 시 `billingReady=false` + 즉시 운영자 알림.
- **`process.exit` 하지 않는다.** 단일 프로세스가 여러 기능을 서빙하면 전체 장애 +
  크래시루프가 된다. degrade 로 간다.
- 프로덕션에서 검증 우회 플래그가 켜져 있으면 그 자체를 문제로 보고한다.
- 알림은 **비즈니스 예외와 진짜 장애를 구분**한다. "잔액 부족"까지 알리면 알림이 무뎌진다.
- 알림 채널 미설정(`ALERT_WEBHOOK_URL` 없음) 자체도 문제 항목에 넣는다.

```ts
const problems: string[] = [];
if (!google) problems.push('GOOGLE_PLAY_SERVICE_ACCOUNT_JSON 누락(안드 결제 검증 불가)');
if (!apple) problems.push('APP_STORE_SERVER_* 누락(iOS 결제 검증 불가)');
if (!webhookSecret) problems.push('STORE_WEBHOOK_SECRET 누락(스토어 웹훅 인증 불가)');
if (isProduction && unverifiedBypass) problems.push('검증 우회 플래그 ON — 위험');
```

**체크**
- [ ] 시크릿 누락 시 부팅 로그에 큰 소리로 남는가
- [ ] 운영자에게 실제로 알림이 가는가
- [ ] 검증 우회 플래그가 프로덕션에서 꺼져 있는가

## 2. 스토어 알림 유실을 전제한 리컨사일 폴링 ★ 최우선

**사고:** Pub/Sub push 엔드포인트가 죽은 개발용 주소(ngrok)를 가리켜 갱신/해지 알림이
**2개월간 한 건도 수신되지 않았다.** 결제를 정상적으로 이어가던 구독자가 만료시각 경과만으로
**조용히 무료로 강등**됐다. 만료 처리된 37명 중 29명이 최근 7일 내 활동한 실사용 유료
사용자였다.

**왜 못 잡았나:** 코드는 완벽했다. 죽은 것은 **인프라 설정**이었고, 사용자는 항의 대신
이탈했다. 이것이 가장 비싼 사고 유형이다.

**필수 구현**

플랫폼별 주기 폴링 크론(권장 6시간). 스토어에 진짜 상태를 직접 물어 원장에 반영한다.

| 플랫폼 | 조회 API | 필요한 키 |
| --- | --- | --- |
| Apple | `GET /inApps/v1/subscriptions/{originalTransactionId}` | originalTransactionId(비밀 아님) |
| Google | `GET .../purchases/subscriptionsv2/tokens/{purchaseToken}` | purchaseToken **원문**(비밀) |

**연장은 적극적으로, 회수는 보수적으로:**

- 연장: 스토어가 활성/유예를 답하면 반영
  - Apple status `1`(active) `3`(billing retry) `4`(grace period)
  - Google `SUBSCRIPTION_STATE_ACTIVE` `SUBSCRIPTION_STATE_IN_GRACE_PERIOD`
- 회수: 스토어가 **명시적으로** 만료/취소/환불을 답했고 **우리가 지금 활성으로 보고 있을 때만**
  - 이미 비활성인 행은 다시 건드리지 않는다(이벤트/알림 스팸 방지)
  - 해지 예약(CANCELED)이라도 만료 전이면 건드리지 않는다
- **조회 실패·JSON 파싱 실패·불확실 상태(ON_HOLD/PAUSED/PENDING) → 아무것도 하지 않는다**

**연장 조건에 반드시 넣을 가드:**

```ts
// 만료시각이 미래이고, 기존 기록보다 뒤일 때만 연장한다.
// 과거 날짜로 갱신 이벤트를 넣으면 보너스만 지급되고 접근은 안 열리는 기형 상태가 된다.
const shouldExtend = Boolean(expiry) && expiry > now && (
  !wasActive || !row.currentPeriodEndsAt || expiry > row.currentPeriodEndsAt
);
```

운영 요건: 다중 레플리카 중복 실행 방지 락(Redis), 부팅 직후 지연 실행(부하 회피),
플랫폼별 시차, 관리자용 수동 실행 엔드포인트(특정 사용자만 즉시 구제).

**체크**
- [ ] 웹훅이 오늘 죽어도 최대 N시간 안에 자동 회복되는가
- [ ] 조회 실패가 권한 회수로 이어지지 않는가 ← 가장 중요
- [ ] 관리자가 특정 사용자만 즉시 리컨사일할 수 있는가

## 3. 재검증에 필요한 원문 보관

**사고:** 보안을 이유로 `purchase_token`을 **해시만** 저장했더니 위 2번 리컨사일을 Google에
대해 구현할 수 없었다. Google 재조회는 토큰 원문이 필수다. 복구가 **매번 콘솔 주문 관리를
사람이 눈으로 대조하는 수작업**이 됐다(주문ID를 스크립트에 하드코딩).

**왜 못 잡았나:** "해시 저장 = 안전"이라는 반사적 판단이 복구 가능성을 지웠다. 해시는
dedupe 용이고 복구용이 아니다.

**필수 구현**

재검증에 필요한 식별자는 **암호화해서** 보관한다.

```ts
// AES-256-GCM. 포맷: v1:<iv>:<tag>:<ciphertext> (전부 base64url)
// 안전 계약 3가지:
//  1. 키 미설정 → 암호화하지 않고 null. 컬럼이 비고 기존 동작과 완전히 동일하다.
//     (키 미설정이 서비스 장애로 번지면 안 된다)
//  2. 복호 실패(키 교체/손상) → 예외가 아니라 null. 크론은 그 행을 건너뛴다(회수 아님).
//  3. 버전 접두어로 이후 키 로테이션/알고리즘 교체 시 식별 가능하게.
```

키는 **서버에서 생성**해 주입한다(`openssl rand -base64 48`). 값이 사람·에이전트의
화면·로그·커밋에 남지 않게 한다.

**소급 적용 한계(반드시 인지):** 컬럼 추가 **이전** 행에는 원문이 없다. 그 사용자들은 앱이
구매 복원을 다시 태울 때 채워진다. 즉 이 조치는 앞으로의 재발을 막고, **이미 강등된
사용자는 별도 복구가 필요하다.** 처음부터 보관했다면 없었을 비용이다.

**체크**
- [ ] 오늘 웹훅이 전부 죽어도 서버 단독으로 구독 상태를 재확인할 수 있는가
- [ ] 그 데이터가 평문으로 DB에 있지 않은가
- [ ] 키가 없을 때 서비스가 죽지 않고 조용히 비활성화되는가

## 4. 멱등성 — 지급/차감은 반드시 1회

**사고 A:** 같은 계정을 여러 기기에서 동시에 쓸 때 차감이 누락됐다(악용 가능).
**사고 B:** 수동 복구 스크립트가 한 주문ID를 공유하는 3개 계정 중 **첫 계정만 반영**하고
나머지는 duplicate로 조용히 스킵됐다.

**필수 구현**

- 이벤트 테이블은 **append-only** + `UNIQUE(platform, store_event_id)`.
- **멱등키에 사용자 식별자를 포함한다.** 한 주문을 여러 계정이 공유할 수 있다.
  - 잘못: `manual_restore:{orderId}` → 첫 계정만 반영
  - 올바름: `manual_restore:{orderId}:{date}:{userId}`
- **경로마다 키 네임스페이스를 나눈다.** 회수(refund/expired)는 같은 주문ID로 이미 기록된
  구매/갱신 이벤트와 유니크 충돌해 조용히 드롭된다.
  - 연장: `{orderId}` 원문 → 웹훅이 살아나도 자연스럽게 합류(중복 지급 없음)
  - 회수: `reconcile_{platform}:{action}:{orderId}` → 별도 키
- 2차 dedupe: `UNIQUE(platform, productId, eventType, purchaseTokenHash)` — 웹훅과 리컨사일이
  같은 환불을 다른 키로 보내와도 교차 합류해 이중 회수를 막는다.
- 트랜잭션 안에서 **이벤트를 먼저 멱등 삽입**하고, 중복이면 구독 행·잔액 생성 없이 중단한다.

**체크**
- [ ] 같은 웹훅을 10번 재전송해도 지급이 1회인가
- [ ] 복구 스크립트를 두 번 돌려도 안전한가
- [ ] 한 주문을 공유하는 여러 계정이 전부 반영되는가

## 5. 스토어 검증 응답을 실제 스펙대로 읽기

**사고:** Google `purchases.products.get`(소모성) 응답에는 **`productId` 필드가 없다.**
`data.productId === input.productId` 비교가 항상 `undefined`라 모든 소모성 결제가
`valid:false`로 처리됐고, 결제한 사용자에게 재화가 지급되지 않았다.

**왜 못 잡았나:** 없는 필드와 비교하면 예외가 아니라 조용한 falsy가 된다. 타입도 잡지 못한다.

**필수 구현**

- 구독과 소모성은 **엔드포인트가 다르다.** 카탈로그의 `kind`로 라우팅하고 **회귀 테스트로
  고정**한다. 소모성 엔드포인트로 구독을 조회하면 스토어가 400/404를 돌려준다.
- 응답 필드는 문서를 보고 검증한다.
  - 소모성: `purchaseState === 0` (URL이 이미 productId로 스코프됨)
  - 구독: `subscriptionState` + `lineItems[].productId` 매칭
- 검증 우회 플래그는 프로덕션에서 절대 켜지 않는다.

**체크**
- [ ] 구독/소모성 각각 실제 스토어 응답으로 통합 테스트했는가
- [ ] 카탈로그의 모든 SKU가 올바른 엔드포인트로 가는 회귀 테스트가 있는가

## 6. 만료 앵커 불변식 — "영구 무료 권한" 방지

**사고 위험:** 만료시각이 **NULL인 active 행**은 기간 검사가 동작하지 않아 해지·만료 후에도
게이트가 **영원히 열린 채로** 남는다.

도달 경로가 실재한다:
1. 스토어 응답의 `expiryTime`이 비어 오면 검증이 `valid:true` + 만료시각 `undefined`를
   돌려주고 그대로 NULL 행이 생성된다
2. 알림에 `expiresDate`가 없을 때도 동일
3. 관리자 수동 이벤트를 만료시각 없이 호출할 때

**필수 구현**

- `active` 상태도 만료 앵커를 **필수**로 강제한다(체험은 `trial_ends_at`, 취소는
  `current_period_ends_at`). 앵커 없는 행은 비활성으로 판정.
- 수동 부여(운영자 지급)만 예외 플랫폼 집합으로 허용한다.
- **적용 전 회수 위험 확인:** 운영 DB에서 기존 유료 행이 이 분기에 걸리지 않는지 먼저 센다.

```sql
SELECT count(*) FROM subscriptions
 WHERE status = 'active' AND current_period_ends_at IS NULL;
-- 0이 아니면 그 행들을 먼저 조사한다. 바로 적용하면 유료 사용자를 자른다.
```

## 7. 결제 실패 유예(grace) — 스토어 실제 정책과 정합

**사고 위험:** 결제 한 번 실패했다고 즉시 끊으면 스토어보다 가혹해져 정상 사용자를 자른다.

- Google Play: 결제 실패 → grace period(개발자 설정 3/7/14/30일, **구독 유지**) →
  account hold(최대 30일) → EXPIRED 최종 종료
- Apple: billing retry(최대 60일) + billing grace period(월 구독 16일) 동안 접근 유지

**필수 구현**

- `past_due` 상태라도 유예 안이면 활성과 동일하게 취급한다(게이트·티어·활성 상품목록 전부).
  여기서 빼면 상위 티어 구독자가 유예 중에 하위 한도로 **강등되는 2차 피해**가 난다.
- 단, 하드 차단(환불 남용/차단)은 유예를 이긴다.

## 8. 티어·게이트 판정은 서버가, 사실 기반으로

**필수 구현**

- 티어는 **활성 구독 행의 productId 사실**로만 판정한다. 게이트로 판정하면 순환이 생긴다.
- 게이트는 **모든 활성 행의 합집합**이다. 대표 행 하나만 보면 체험+유료 공존 시 어느 행이
  최신이냐에 따라 유료 게이트가 사라지는 회귀가 생긴다.
- 상위 SKU를 하나라도 보유하면 상위 티어로 올라간다(다운그레이드 방지).
- 판매 중단된 레거시 SKU는 **별도 티어**로 유지한다. 신규 SKU와 한도를 같게 하면 업그레이드
  동기가 0이 되고, 무료와 같게 하면 유료 사용자를 배신한다.
- 클라이언트는 어떤 헤더·바디로도 티어에 영향을 주지 못한다. 관리자 판정은 서버 역할 조회에서만.

**⚠ 레거시 SKU 함정(실제 사고):** 한도 설정에서 레거시 티어 셀을 비워 두면 폴백
(`legacy ?? free ?? paid`)으로 **무료 수준까지 떨어진다.** API 스키마에서 레거시 티어 필드가
빠져 있던 동안 관리자가 저장할 때마다 모든 기능의 레거시 한도가 조용히 잘렸다.
**스키마·저장·회귀 테스트 3곳 모두**에 티어가 등재돼야 한다.

## 9. 구매 복원 경로 — 판매 중단 SKU 화이트리스트

**사고 위험:** 신규 클라이언트는 서버에서 현행 SKU만 받는다. 판매 중단된 레거시 구독을
스토어에서 복구해도 **매칭에 실패해 서버 검증까지 가지 못한다.** 레거시 구독자가 영원히
무료로 남는다.

**필수 구현**

- 복원 매칭 맵 = 서버가 내려준 상품 + **레거시 화이트리스트**. 서버가 같은 productId를
  내려주면 서버 정보가 우선.
- 계정 전환/로그인 직후 **조용히 1회 자동 복원**을 태운다(사용자가 버튼을 누르기 전에).
  - 이미 구독자면 스토어를 건드리지 않는다
  - 실패는 조용히 삼킨다(로그인 흐름을 절대 막지 않는다)
  - 계정당 세션 1회
- **한계 인지:** 이미 로그인된 채 계속 쓰는 사용자는 이 경로를 타지 않는다. 장기 미접속·
  강등 상태 사용자를 위한 백필을 별도로 설계해야 한다.

## 10. 웹훅 수신 인프라 자체의 감시

**사고:** 코드는 완벽했지만 **push 엔드포인트 설정**이 죽은 주소를 가리켰다. 코드 리뷰로는
절대 못 잡는다.

**필수 구현**

- 수신한 웹훅을 **인박스 테이블에 원문 그대로 적재**하고 처리 상태를 남긴다.
- 미처리 웹훅 누적 시 운영자 알림.
- **"최근 N시간 갱신 이벤트 0건"을 이상 신호로 감시한다.** 이게 있었으면 2개월이 아니라
  하루 만에 발견됐다.
- Pub/Sub OIDC 토큰 검증 + 공유 시크릿 헤더로 위조 차단.

```sql
-- 웹훅 생사 판별. 0이면 인프라 설정을 즉시 의심한다.
SELECT count(*) FROM entitlement_events
 WHERE event_type = 'renewal' AND created_at > now() - interval '24 hours';
```

## 11. 스키마 함정 — 정수 오버플로우·길이 제한

**사고 A:** 자동화 결제 이벤트가 **0건 적재**됐다. 원인은 컬럼이 `integer`인데 외부 식별자가
int32를 넘겼기 때문. 삽입이 실패하는데 결제 흐름은 계속 진행됐다.
**사고 B:** 긴 외부 URL이 `varchar(512)`를 넘겨 특정 계정만 로그인 500.

**필수 구현**

- 외부 시스템 식별자는 `bigint`/`text`. int32를 넘는 값은 실재한다.
- **원장 삽입 실패가 조용히 넘어가지 않게** 한다. 결제 기록 실패는 결제 실패로 취급.

## 12. 과금 정책은 코드보다 먼저 문서로 확정

**사고:** AI 생성 기능에서 "생성 시점 차감"과 "성공 시점 차감"이 코드마다 달라 과다 차감이
발생했고, 운영 보상 환불을 실행해야 했다.

**필수 구현**

- 차감 시점을 **한 문장으로** 확정하고 문서에 박는다.
  예: "생성=차감. 등록 성공 여부와 무관. 실패 건은 환불이 아니라 재등록으로 구제한다."
- 구버전 클라이언트 대비 **마커 헤더**로 신/구 동작을 분기하고, 마커 없는 요청에는 보수적
  상한을 적용한다.
- **누적 스냅샷 컬럼을 per-run 합산에 쓰지 않는다.** 누적값을 더하면 실제보다 몇 배 큰
  과다 차감으로 오인한다. 검증은 원장(charges/events)으로 한다.

## 13. 집행 스위치와 실제 집행의 분리

- 한도 집행 모드는 `off`가 기본이어야 한다(구버전 클라이언트 무영향).
- 단, **신버전 클라이언트는 마커로 강제 집행**한다. 그래야 집행 모드가 꺼져 있어도 현행
  앱은 한도가 적용된다.
- 자원 보호 상한(요청당 최대 건수)은 집행 모드와 **무관하게 항상** 적용한다.

## 14. 운영 적용 완료는 폐쇄루프로 증명

**사고:** 웹훅 코드와 운영 URL은 존재했지만 topic 또는 push 구독이 없거나, OIDC 설정이 맞지 않아
실제 갱신 알림이 장기간 0건이었다. 상태 엔드포인트가 HTTP 200이어도 결제 readiness의 일부가
false였고, 콘솔의 "저장 완료"는 전달 성공을 증명하지 못했다.

**필수 구현·검증**

- topic과 **push subscription을 별개 자원으로** 확인한다. topic만 있으면 메시지는 전달되지 않는다.
- 인증 push는 webhook URL을 explicit audience로 고정하고, 백엔드는 audience와 service-account email을
  모두 검증한다.
- Pub/Sub 서비스 에이전트에는 서비스 계정 토큰 생성 권한, 스토어 게시자에는 topic publish 권한이
  있어야 한다. 권한 이름만 확인하고 credential 값은 출력하지 않는다.
- 스토어 콘솔의 테스트 알림을 보내 **스토어 → topic → 인증 push → 운영 endpoint → inbox** 도착까지
  확인한다. 테스트 페이로드가 `unsupported_notification`으로 기록되는 것은 transport 증거일 수 있지만,
  실제 renewal 처리 성공 증거는 아니므로 두 증거를 구분한다.
- HTTP 200만 보지 말고 billing readiness의 store credential, webhook secret, owner alert,
  unverified bypass 항목을 각각 확인한다.
- 암호화 재검증 토큰 보유율을 측정하고, 컬럼 추가 전 레거시 행은 구매 복원·보안 입력 파일 기반
  대조 등 별도 백필 계획을 둔다. 보유율이 낮으면 "자동 복구 완비"라고 보고하지 않는다.
- 수동 복구 대상 주문번호·토큰은 tracked source에 새로 하드코딩하지 않는다. untracked 입력 파일이나
  표준입력으로 받아 dry-run/apply 요약만 남긴다.

**완료 판정 체크**

- [ ] 운영 billing readiness가 의도한 모든 항목에서 true인가
- [ ] 테스트 알림이 운영 inbox에 도착했는가
- [ ] 실제 renewal 이벤트의 멱등 처리 회귀 테스트가 통과했는가
- [ ] 레거시 토큰 보유율과 미커버 사용자 복구 계획을 보고했는가

## 15. 스토어 상품 등록 완료와 운영 조회 가능은 별개

**사고:** 신규 iOS 구독의 productId·가격·현지화는 등록돼 있었지만 판매 국가/지역과 심사 정보
스크린샷이 빠져 `제출 준비 중`에 머물렀다. 앱은 상품을 조회하지 못해 업그레이드가
`StoreKit: Failed to get response from platform.`으로 전량 실패했다. Google Play의 같은 SKU는
이미 활성이라 플랫폼별 상태가 달랐다.

**필수 구현·검증**

- App Store: productId 존재만 보지 말고 사용 가능 국가/지역, 가격, 현지화, 심사 스크린샷,
  심사 제출·승인 상태를 각각 확인한다.
- Google Play: 구독 항목과 base plan을 구분하고 자동 갱신 기간, 대상 국가/지역, `활성` 상태를
  확인한다. 레거시 업그레이드는 기존 구매 토큰을 넣은 교체 파라미터를 테스트한다.
- 스토어별 상태를 다른 플랫폼에서 추정하지 않는다. 같은 productId라도 출시 상태는 독립이다.
- 결제 실기기 검증은 스토어에서 설치한 빌드로 한다. ADB/직접 설치본의 `installer=null` 또는
  Play 서명 불일치는 Google Play Billing이 의도적으로 차단한다.
- 플랫폼 원문 오류는 로그에만 남기고 사용자에게는 재시도·스토어 로그인 안내를 제공한다.

**완료 판정 체크**

- [ ] App Store 신규 SKU가 판매 지역·심사 자료를 갖추고 제출 또는 승인 상태인가
- [ ] Google Play 신규 SKU의 base plan이 대상 국가에서 활성인가
- [ ] 레거시 → 신규 업그레이드가 이중 구독이 아닌 교체 파라미터로 테스트됐는가
- [ ] 스토어 설치 실기기에서 상품 조회와 결제 확인창 진입(결제 없이 취소)이 검증됐는가
- [ ] 승인 후 운영 앱에서 모든 productId 조회 결과가 비어 있지 않은가
